# Build the tools in-page, keep the bridge local

Status: research survey, 2026-11-17, sourced inline; the per-topic notes are in `process/browser-agent-integration-notes/`. Informed the 2026-11-17 decision in `process/DECISIONS.md` that the hosted site offers no agent automation surface; its "near-term changes" carried into `process/AGENTIC_AUTHORING.md`. Some product dates rest on secondary sources, marked as such in the notes.

As of 17 November 2026, no cross-browser standard lets a web page offer tools to an AI agent. **WebMCP** (`document.modelContext.registerTool()`) runs as a Chromium origin trial: Chrome from 149 (June 2026) and Edge from 150 (September 2026). Mozilla's position is **neutral**, WebKit's is **oppose**, and it is shipped by default nowhere. MCP itself still has **no browser, postMessage or WebSocket transport**. The community project MCP-B fills that gap with a polyfill and a localhost relay. Reaching `ws://localhost` from a hosted https page now works in Chrome (147+), Edge and Firefox (154+), but only after a one-time per-site permission prompt. Safari still blocks it outright as mixed content. The agents people actually use — Claude in Chrome (GA August 2026), Gemini in Chrome auto browse, the ChatGPT Chrome extension (Atlas was shut down on 9 August 2026), Comet and the Playwright and DevTools MCP servers — read pages mainly through the **accessibility tree** and screenshots. None of them is documented as consuming WebMCP or llms.txt. Every vendor says prompt injection is unsolved, with residual attack rates of about 0–2% per attempt under layered safeguards, and higher under repeated attack. For SEED.html this points to (A): an in-page tool surface that sits behind a consent gesture and an AbortController, built on the tool module the bridge already relays to. Hosted-origin access to the bridge (B) should be a later, opt-in transport for Chromium and Firefox only, gated by a pairing token. The groundwork that helps either way is mostly accessibility and undo work SEED.html already favours.

## WebMCP is a Chromium origin trial that WebKit opposes

WebMCP is a Google and Microsoft incubation in the W3C Web Machine Learning Community Group. Its current text is a **Draft Community Group Report dated 13 November 2026** that is explicitly "not a W3C Standard nor on the W3C Standards Track" ([WebMCP spec](https://webmachinelearning.github.io/webmcp/)). The API moved during 2026. Chrome deprecated `navigator.modelContext` in Chromium 150 and dropped `provideContext()`, `clearContext()` and `unregisterTool()`. Its guide now recommends feature detection with `'modelContext' in document` ([Chrome guide](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/agentic-javascript-tools.md.txt)). The current interface is `[SecureContext]` and has three methods: `registerTool(tool, {exposedTo, signal})`, `getTools()` and `executeTool()`. To unregister a tool, the page aborts the signal it passed in. Tools carry a `name`, `description`, `execute`, optional JSON Schema input and output, and advisory annotations: `readOnlyHint`, `untrustedContentHint`, `consequentialHint` (added in Chrome 154) and `debugging` (Chrome 156) ([WebMCP spec](https://webmachinelearning.github.io/webmcp/)). Chrome warns that "the browser does not validate input or apply defaults", so the page's `execute` has to do both ([Chrome guide](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/agentic-javascript-tools.md.txt)). A declarative variant puts `toolname` and `tooldescription` attributes on `<form>`. The README says it "is not part of the specification at this time", and its schema synthesis is still "TBD" ([declarative explainer](https://github.com/webmachinelearning/webmcp/blob/main/declarative-api-explainer.md)). Usage reflects this. Chrome's origin-trial data shows about **172 million imperative registrations against about 20,000 declarative** ([TAG review #1238](https://tag-github-bot.w3.org/gh/w3ctag/design-reviews/1238)).

The objections are substantive and shape any implementation. **WebKit** argues that agent problems belong in HTML and ARIA rather than a parallel tool layer. It says consent is missing and the consent hook is a TODO, that cross-origin security is unexamined, and that over-parameterized tools enable tracking. It has proposed a new community group and a W3C workshop instead ([WebKit #670](https://github.com/WebKit/standards-positions/issues/670)). **Mozilla** warns that a site's tools may not match its UI. It also points out that "no MCP protocol is involved" despite the name, and that invocation is limited to browser vendors' own agents. It wants WebExtension and WebDriver BiDi integration instead ([Mozilla #1412](https://github.com/mozilla/standards-positions/issues/1412)). The spec has **no per-call user confirmation**. Gating comes from a `tools` Permissions Policy (default `'self'`), a secure context, same-origin visibility by default and opt-in `exposedTo` for cross-origin callers. Chrome tells developers to treat `consequentialHint` "as a hint, not an enforcement mechanism" and to keep their own in-app confirmation ([Chrome guide](https://developer.chrome.com/docs/modern-web-guidance/guides/webmcp/agentic-javascript-tools.md.txt)). That gap matters for SEED.html. A page that registers tools only after the user makes a consent gesture is applying a stricter policy than the spec requires. That fits the spec, and it is the right default.

Reach is narrower than the name suggests. In the spec, tools are visible to the registering document, same-origin documents in its tree, and "built-in agents". In practice Chrome lets extensions enumerate and call tools from content scripts. That is how Google's two sample agents work, and Google describes both as "separate from Gemini in Chrome" ([Chrome WebMCP docs](https://developer.chrome.com/docs/ai/webmcp)). Edge pairs WebMCP with `aria-actions`, an accessibility-framed way to expose secondary widget actions. A TAG reviewer objected to repurposing ARIA for agents with the line "assistive technology is for people" ([Edge blog](https://blogs.windows.com/msedgedev/2026/09/21/new-in-edge-for-developers-create-better-components-and-make-your-site-agent-ready/); [TAG #1238](https://tag-github-bot.w3.org/gh/w3ctag/design-reviews/1238)).

## MCP has no browser transport, so MCP-B fills the gap

MCP defines only stdio and Streamable HTTP. The **2026-07-28 revision** proposed deprecating HTTP+SSE, made the core stateless and added MCP Apps and Tasks as extensions. It added no browser transport ([AAIF blog](https://aaif.io/blog/mcp-2026-07-28-whats-changing-and-how-to-migrate)). A postMessage transport proposal, SEP-1005, was closed as dormant on 24 November 2025 because maintainers want to "keep the amount of transports small". The earlier WebSocket proposal #493 was never picked up ([SEP-1005](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/1005); [#493](https://github.com/modelcontextprotocol/modelcontextprotocol/issues/493)). postMessage appears in MCP only inside **MCP Apps**, which runs server-provided UI in sandboxed host iframes. That is the opposite direction from a page offering tools ([ext-apps spec](https://github.com/modelcontextprotocol/ext-apps/blob/main/specification/2026-01-26/apps.mdx)). For transports a browser can reach, the spec's rule is strict: servers **MUST validate Origin** on every connection, SHOULD bind to 127.0.0.1 and SHOULD authenticate ([MCP Streamable HTTP](https://modelcontextprotocol.io/specification/latest/basic/transports/streamable-http)). The official TypeScript, Python and Go SDKs all shipped without DNS-rebinding protection on by default (CVE-2025-66414, CVE-2025-66416, CVE-2026-34742) ([CSA research note, 9 Nov 2026](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-transport-trust-gap-20261109-csa-style/)). The textbook case of a browser-reachable local server going wrong is still **Zoom's port-19421 server** in 2019, which any website could drive ([Zoom ZSB-19001](https://www.zoom.com/en/trust/security-bulletin/ZSB-19001/)).

**MCP-B** is the community answer. It is MIT-licensed and says of itself "not an official W3C or MCP project". It grew out of Alex Nahas's original WebMCP prototype and now ships several pieces: a `document.modelContext` polyfill, an MCP bridge that adds resources and prompts, transports (tab postMessage, iframe and Chrome extension), a Chrome extension, and **`@mcp-b/webmcp-local-relay`**. The relay forwards a site's tools to desktop clients such as Claude Desktop, Cursor and VS Code ([WebMCP-org/npm-packages](https://github.com/WebMCP-org/npm-packages)). The polyfill wraps a native implementation where one exists, and 3.x targets `document.modelContext` ([@mcp-b/global README](https://unpkg.com/@mcp-b/global@latest/README.md); [pkgstats](https://www.pkgstats.com/pkg:@mcp-b/webmcp-polyfill)). Adoption is modest: the main repo has 107 stars, `@mcp-b/global` is already on v6, and the relay's security model is undocumented. It is a real option, but it is a dependency to pin and isolate, not a foundation.

## Localhost from https: three engines prompt, Safari refuses

Chrome replaced the CORS-preflight design, Private Network Access, with **Local Network Access (LNA)**, which asks the user for permission ([Chrome blog](https://developer.chrome.com/blog/local-network-access)). The rollout was staged. Chrome 142 (October 2025) gated fetch, subresources and iframes. Chrome 145 split the permission into `local-network` and `loopback-network`, the latter labelled **"Apps on device"**, and users who had allowed the old permission must allow again ([Chrome LNA guide](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access.md.txt); [Figma help](https://help.figma.com/hc/en-us/articles/34458998159511-Local-network-access-in-Figma)). **Chrome 147 (7 April 2026)** brought WebSocket and WebTransport connections to local addresses under the prompt ([Chrome 147 release notes](https://developer.chrome.com/release-notes/147)). Crucially, `ws://localhost`, `ws://127.0.0.1` and `ws://[::1]` from an https page are **exempt from mixed-content blocking**. Once the user clicks Allow for the site, connections are silent ([Chrome LNA guide](https://developer.chrome.com/docs/modern-web-guidance/guides/security/local-network-access.md.txt)). Three practical details follow. Workers cannot trigger the prompt, so the window must ask first. Extensions with host permissions are exempt from LNA. And a dev copy served from `http://localhost:5173` makes a local-to-loopback connection, which LNA does not yet gate, so **developers never see the prompt their users will see** unless they apply `Content-Security-Policy: treat-as-public-address` ([Microsoft Learn: Edge LNA](https://learn.microsoft.com/en-us/deployedge/ms-edge-local-network-access)).

| Engine                      | `ws://localhost` from an https page                                                     | Since                                                                                                                                                                                                                                           |
| --------------------------- | --------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Chrome                      | Allowed after one "Apps on device" grant per site                                       | WebSocket gating in 147, 7 Apr 2026 ([notes](https://developer.chrome.com/release-notes/147))                                                                                                                                                   |
| Edge                        | Same as Chrome (LNA default from Edge 143); WebSocket milestone not stated by Microsoft | [Microsoft Learn](https://learn.microsoft.com/en-us/deployedge/ms-edge-local-network-access)                                                                                                                                                    |
| Firefox                     | Allowed after a "Device apps and services" grant                                        | LNA default for all in 153, 21 Jul 2026 ([notes](https://www.firefox.com/firefox/153.0/releasenotes/)); WebSockets in 154, Aug 2026 ([Linuxiac](https://linuxiac.com/firefox-154-adds-websocket-local-network-protection-and-new-ai-controls/)) |
| Safari (macOS, iOS, iPadOS) | **Blocked as mixed content**                                                            | Bug 171934 open since 2017 ([WebKit](https://bugs.webkit.org/show_bug.cgi?id=171934))                                                                                                                                                           |

Safari is the hard wall. WebKit bug 171934 remains NEW. Comments through August 2026 note that every other engine ships LNA and that Shopify, Zotero and others send Safari users elsewhere ([WebKit bug 171934](https://bugs.webkit.org/show_bug.cgi?id=171934)). WebKit landed internal LNA plumbing on 11 September 2026, but treats "Prompt" as "Denied" because "no native permission prompt exists yet" ([WebKit bug 319907](https://bugs.webkit.org/show_bug.cgi?id=319907)). Apple's John Wilander has said WebKit "has long opposed broad localhost access" and has floated a single-port "latch mode" instead ([WebKit bug 171934](https://bugs.webkit.org/show_bug.cgi?id=171934)). The known workarounds are a locally trusted certificate for `wss://localhost` or a public DNS name that resolves to 127.0.0.1. Both are too heavy for authors of family books.

On the storage side, **FileSystemObserver** shipped on Chrome desktop in **Chrome 133 (4 February 2025)** and explicitly covers the Origin Private File System ([Chrome 133 release notes](https://developer.chrome.com/release-notes/133)). It is still non-standard (whatwg/fs PR #165). Gecko signalled positive and WebKit gave no signal, and neither has shipped it ([blink-dev I2S](https://www.mail-archive.com/blink-dev@chromium.org/msg12265.html); [MDN](https://developer.mozilla.org/en-US/docs/Web/API/FileSystemObserver)). OPFS is origin-scoped, so the only writers it can report are same-origin code: another tab, a worker, or an agent running JavaScript in the page.

## Agents read the accessibility tree and act through extensions

The product landscape consolidated in 2026. **Claude in Chrome** was reported generally available for paid plans on 26 August 2026 ([ccleaks](https://ccleaks.com/news/claude-in-chrome-generally-available-aug-2026)). **Gemini in Chrome auto browse** launched for US Pro and Ultra subscribers on desktop on 28 January 2026 and reached US Android in August ([9to5Google](https://9to5google.com/2026/01/28/chrome-gemini-auto-browse/); [Neowin](https://www.neowin.net/news/gemini-is-now-available-in-chrome-with-agentic-auto-browse-for-all-android-users-in-the-us/)). OpenAI discontinued **Atlas** on 9 August 2026 ([TechCrunch](https://techcrunch.com/2026/07/09/openai-is-shutting-down-atlas-but-its-ai-browser-ambitions-are-still-growing/)) and gave its Chrome extension a tab-controlling "Work" mode around 15 October ([Unite.AI](https://www.unite.ai/openai-brings-computer-use-to-chrome-with-chatgpt-tab-controls/)). **Opera Neon** turned the browser itself into an MCP server for external clients on 31 March 2026 ([Opera press](https://press.opera.com/?p=3885)). **Brave** AI browsing is an opt-in early test in all channels, in a separate profile that cannot see the main profile's state ([Brave blog](https://brave.com/blog/ai-browsing/)). Firefox and Safari have no native agent equivalent in this survey.

Perception converges on the accessibility tree. Playwright MCP prefers its accessibility snapshot to screenshots and acts on element references taken from it ([Playwright MCP](https://github.com/microsoft/playwright-mcp)). Stagehand v3 stitches per-frame accessibility trees together, including out-of-process iframes, and patches `attachShadow` to keep shadow roots open ([Browserbase](https://browserbase.com/blog/taming-iframes-a-stagehand-update)). OpenAI stated that Atlas "uses ARIA tags—the same labels and roles that support screen readers" and told site owners that accessibility helps its agent ([OpenAI](https://openai.com/index/introducing-chatgpt-atlas/)). Adrian Roselli counters that ARIA-for-agents advice will push sites to misuse ARIA instead of writing semantic HTML ([Roselli](http://adrianroselli.com/2025/10/openai-aria-and-seo-making-the-web-worse.html)). One operational detail matters directly for SEED.html. Anthropic documents that **JavaScript `alert`, `confirm` and `prompt` dialogs block browser events and stall Claude in Chrome**. It also documents a 10 MB upload cap and refusal of credential-named files ([Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)). Claude in Chrome bridges to Claude Code through a native-messaging host plus a cloud relay, which sidesteps LNA entirely ([Claude Code Chrome docs](https://code.claude.com/docs/en/chrome)). No product surveyed documents consuming WebMCP, and none documents reading llms.txt while acting on a page.

The consent models are similar across products. Claude in Chrome offers per-site Allow, Allow-once and Deny, and confirms before downloads, sensitive data and authorizations even under a site-wide grant ([Claude permissions guide](https://support.claude.com/en/articles/12902446-claude-in-chrome-permissions-guide)). Gemini asks for confirmation before it modifies data or submits web forms, and requires the user to take over to finish purchases or accept terms of service ([Chrome Help](https://support.google.com/chrome/answer/16821166?hl=en)). Gemini's rule could plausibly prompt the user on every save in an editor. A declared tool with an honest `readOnlyHint` or a scoped write could reduce that friction.

## Injection stays unsolved, and the frameworks limit agency instead

Vendor numbers are sobering and not comparable with each other. Anthropic's November 2025 browser research measured adaptive Best-of-N attacks at **8.0–13.8% raw success, falling to 1.4–2.4% with improved safeguards**, and stated that "no browser agent is immune to prompt injection" ([Anthropic](https://www.anthropic.com/research/prompt-injection-defenses)). OpenAI conceded the problem is unlikely ever to be fully solved and moved to RL-trained attackers ([OpenAI](https://openai.com/index/hardening-atlas-against-prompt-injection)). Google built a **User Alignment Critic** that sees only action metadata, never raw web content, and per-task **Agent Origin Sets** that split origins into read-only and read-write ([Google](https://blog.google/security/architecting-security-for-agentic/)). "The Attacker Moves Second", by authors from OpenAI, Anthropic and Google DeepMind, broke **all 12** published defences it tested under adaptive attack, mostly above 90% success ([arXiv 2510.09023](https://arxiv.org/abs/2510.09023)). The attack shapes that matter for a document editor are documented. Brave showed nearly invisible text in content being executed as commands ([Brave](https://brave.com/blog/unseeable-prompt-injections/)). EchoLeak and CamoLeak exfiltrated data through rendered images fetched via trusted proxies ([Willison on EchoLeak](https://simonwillison.net/2025/Jun/11/echoleak/); [The Register on CamoLeak](https://www.theregister.com/2025/10/09/github_copilot_chat_vulnerability/)).

The frameworks therefore limit capability rather than trusting filters. **Meta's Agents Rule of Two** says an agent should combine at most two of three things: processing untrusted input, accessing private data, and changing state or communicating externally. If it needs all three, it needs supervision ([Meta AI](https://ai.meta.com/blog/practical-ai-agent-security/)). That follows Willison's "lethal trifecta" ([Willison](https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/)). The **OWASP Top 10 for Agentic Applications 2026** centres on "least agency" ([OWASP](https://genai.owasp.org/resource/owasp-top-10-for-agentic-applications-for-2026)). The MCP spec says there **SHOULD always be a human in the loop** able to deny calls. It also says tool inputs should be shown before a call, and that clients **MUST treat tool annotations as untrusted** unless the server is trusted ([MCP spec: Tools](https://modelcontextprotocol.io/specification/2025-11-25/server/tools)).

The conventions for instructions written for agents are informal. **AGENTS.md** is now stewarded by the Linux Foundation's Agentic AI Foundation, formed on 9 December 2025 alongside MCP ([Linux Foundation](https://www.linuxfoundation.org/press/linux-foundation-announces-the-formation-of-the-agentic-ai-foundation)). It is plain Markdown, the nearest file wins, and "explicit user chat prompts override everything". It claims 60k+ projects, a self-reported figure, and its only security content is a suggested "security considerations" section ([agents.md](https://agents.md/)). Tools protect themselves from untrusted repositories with workspace-trust gates: Claude Code shows a trust dialog and requires separate approval for project MCP servers ([Claude Code security](https://code.claude.com/docs/en/security)). Those gates fail when they are off. Cursor shipped with Workspace Trust disabled, and a malicious repo ran tasks as soon as it was opened ([Oasis Security](https://www.oasis.security/blog/cursor-security-flaw)). Injected agents are known to **persist by editing AGENTS.md** and similar files ([SafeDep](https://safedep.io/agent-skills-threat-model/)). A January 2026 audit found about 12% of skills in one registry malicious ([Snyk](https://snyk.io/articles/skill-md-shell-access/)). **llms.txt** is widely published and rarely read. Ahrefs found 97% of the files it studied received zero AI requests ([PPC Land](https://ppc.land/llms-txt-adoption-rises-8-8x-but-97-of-files-get-zero-ai-requests/)), and Google calls it unnecessary for AI search ([Optimizely](https://www.optimizely.com/field-notes/articles/does-llms-txt-work/)). Its real niche is documentation indexes.

## What this means for SEED.html: choose the transport, not the tool set

The A-versus-B framing hides a useful fact about SEED.html's current architecture. `scripts/agent-bridge.mjs` is a stdio MCP server that relays every tool call over the WebSocket to the app module (`src/lib/agent-bridge/module.js`). The module, running in the tab, is what actually reads and writes OPFS. So **the tools already live in the page**. A and B are two transports onto the same tool core. A exposes that core to agents running inside the browser. B exposes it to desktop agents such as Claude Code on the hosted origin, instead of only on a locally served copy. Today `verifyClient` accepts any origin whose host is `localhost`, `127.0.0.1` or `[::1]`, on any port. That is why the hosted origin is shut out today.

**Option B** (open the bridge to `https://readitinabook.com`) is technically feasible on Chrome 147+, Edge and Firefox 154+. Each user clicks through an "Apps on device" or "Device apps and services" prompt once. It is **impossible on Safari and on any iPad**, where there is no local bridge process anyway. Its security case is weaker than it looks. Browsers do not let pages forge Origin, so allowlisting the hosted origin keeps other websites out. But any script that runs on readitinabook.com gets the same standing: an XSS, or book content executing in a same-origin preview frame. It would sit at the bridge's door with the same Origin as the app, so the consent gesture inside the app would be the only remaining gate. B also hands a desktop agent that usually has a shell and network access (private data plus external communication) a stream of untrusted book text. That is the full Rule-of-Two trifecta, which is exactly why the `book-editor` agent is restricted. If B ships, it should require a pairing token shown in the terminal and entered in the app, and add an explicit Host check. Ask for the LNA permission with a `fetch` at a moment the app chooses, rather than letting a bare WebSocket attempt trigger it. And present the feature as power-user plumbing, not the main agent story.

**Option A** (an in-page surface behind a consent gesture) works with the agents users are actually installing, which already run in the user's profile and therefore see the same OPFS origin. The design that follows from the evidence has six parts. First, a thin adapter that calls `document.modelContext.registerTool()` when `'modelContext' in document`, with an origin-trial token for each of Chrome and Edge. Second, an AbortController owned by the consent toggle, so revoking consent unregisters every tool. Third, honest annotations: `readOnlyHint` on reads, `consequentialHint` on deletes, overwrites and anything that publishes, and `untrustedContentHint` on every result that carries book text. Fourth, input validation inside `execute`, because the browser does none. Fifth, a `tools=()` Permissions-Policy on preview frames, so book content can never register tools. Sixth, the app's own confirmation dialog for consequential actions, because the hints bind no one. The honest caveat is reach. As of today no mainstream agent is confirmed to consume WebMCP. Gemini's support is "soon" and the origin trial's end date is unconfirmed. The surface is a forward bet, and in the near term **well-labelled UI is what those agents will actually use**. MCP-B's relay could later carry the same registrations to desktop clients without SEED.html running its own hosted-origin socket, at the cost of a community dependency.

The recommendation is A as the strategic direction and B kept as it is. Refactor the bridge module into a transport-neutral tool core with a fixed, project-scoped grant: read and write split up front, in the spirit of Origin Sets. Expose it through WebMCP behind consent. Leave the WebSocket bridge restricted to locally served origins, where it already serves the author's own workflow. Revisit hosted-origin B only if users ask for Claude Code against readitinabook.com, and then only with pairing.

### An AGENTS.md inside a book's SOURCE folder is untrusted input with extra pull

A brief shipped inside a book is the repository-instructions problem in document form. Agents are built to follow these files, so a book that arrives from someone else carries an instruction channel with more authority than its prose. No vendor guidance covers instruction files embedded in user documents, but the code-repository practice transfers directly. Treat the file as **data until the user trusts the project**. Show its presence and contents in the UI, and serve it to agents through a read tool marked `untrustedContentHint`, rather than injecting it into tool descriptions or the consent screen. Make trust a per-project, revocable act that defaults off for imported projects, and reset it when an import or sync changes the file. Keep the AGENTS.md precedence rule: the user's prompt overrides the brief. Because injected agents persist by rewriting instruction files, **writes to AGENTS.md (and CLAUDE.md) should always need confirmation with a visible diff**, even in a session that otherwise auto-approves writes. The same treatment applies to transform scripts and stylesheets, which are the book's executable surface. Supporting the AGENTS.md filename rather than a SEED.html-specific name is the right call for cross-agent compatibility.

### Near-term changes that pay off under either choice

Several changes are worth making whichever transport wins. **Replace the remaining native dialogs.** A grep of `src/` finds seven native `confirm()` call sites, each of which stalls Claude in Chrome and blocks automation. They are in `src/App.svelte` (three), `src/lib/navigation/views/PublishView.svelte`, `src/lib/components/SpineSidebar.svelte`, `src/lib/components/manifest/ManifestContainer.svelte` and `src/lib/components/spine/EditorPane.svelte`. In-page `<dialog>` confirmations like the existing review dialogs keep the human gate and show up in the accessibility tree. **Audit accessible names** on every control an agent needs, especially `<select>`-driven panels and custom listboxes. Avoid closed shadow roots, and keep key state reachable without hover. This is house style already, and it is the one baseline every surveyed agent shares and WebKit's alternative endorses. **Observe changes.** Use FileSystemObserver on the project directory in Chrome and Edge, with a BroadcastChannel announcement from every writer as the fallback in Firefox and Safari. SEED.html already uses BroadcastChannel in the plugin layer. The editor then refreshes whenever a second tab, a worker or an agent's `javascript_tool` writes OPFS behind its back. **Checkpoint agent turns.** Snapshot the project before each agent session or batch of writes, and keep a visible log of which tool wrote which file, with one-step revert. Because every agent write passes through the app, SEED.html can avoid the blind spots Claude Code's checkpoints document for shell-made and external edits ([Claude Code checkpointing](https://code.claude.com/docs/en/checkpointing)). Finally, **close exfiltration channels**. When the agent surface is active, the preview should not fetch remote images, fonts or CSS from book content, which is the EchoLeak and CamoLeak lesson applied to EPUB.

## Conclusion

The 2026 picture inverts the usual standards story. The proposed tool API (WebMCP) is in a single-engine trial with an active opposition. The things that actually work across agents today are old: semantic HTML, accessible names and dialogs that do not block the event loop. For SEED.html, the decision that matters is not whether to adopt WebMCP or open the bridge. It is to make the tool core transport-neutral, project-scoped and self-enforcing, with confirmations, annotations, checkpoints and trust gates that the app applies itself, because no browser, spec or agent will apply them for it. With that core in place, WebMCP, MCP-B's relay and a paired hosted-origin bridge become cheap adapters that SEED.html can switch on as each matures, rather than bets it has to win in advance.

The main uncertainties to watch are four: the WebMCP origin-trial end milestone and any W3C workshop outcome around TPAC; whether Gemini in Chrome or Claude in Chrome starts consuming declared tools; whether WebKit ships an LNA prompt or "latch mode", which would bring Safari back into reach for B; and whether FileSystemObserver reaches Firefox.
